## 2. 当前 Web 产品与 iOS 保留范围

下表记录实际 Web 行为。PIN／会话两行仅为调研事实，按 Gordon 的明确指示不移植；其余行为除明确列出的差异外保留。Web 的公开 URL 访问限制不等同于本地 App 的产品需求。

| 页面／状态 | 实际行为 |
|---|---|
| PIN 页 | 六位数字，输满自动验证；自带 0–9 和删除键。错误后清空并提示“密码不正确，请再试一次”。没有注册、设置 PIN、修改 PIN、找回密码或生物识别。 |
| 主页面 | 默认任务页；顶部显示累计余额、月日、中文星期及当日净变化。任务／奖励是顶部切换按钮，不是底部导航；页头随整页滚动，不吸顶。没有日期选择器。 |
| 任务 | 32 项，整张卡片点击加分；可重复完成，无每日次数上限。角标是**当天净完成次数**，不是累计次数或复选状态。 |
| 奖励 | 9 项，直接点击兑换，无二次确认。每次扣固定分数并增加当天次数；余额不足禁用，够分可重复兑换。 |

| 关闭弹层 | ×、背景点击或 Escape 可关闭；保存中不能关闭／重复提交；保存成功关闭并反馈，失败保留弹层和输入。 |
| 保存／刷新 | Web 先写 IndexedDB，再同步服务器；刷新后保留积分和计数，但回到任务页、退出撤销并关闭弹层。显式锁定不清除积分。 |

积分不变量：只接受固定目录的 ID 和分值；余额 ≥ 0；各日任务／奖励次数 ≥ 0。没有额外每日积分上限，也没有用户可见的累计积分上限。计数与余额同时成功或同时失败；拒绝的动作不算一次操作。

**已观察到的 Web 特例，不能隐瞒：**完成洗脸两次、刷牙一次得到 5 分，兑换棒棒糖后余额 0；此时仍可点“撤销刷牙”，Web API 返回 409，最终余额仍为 0、刷牙次数仍为 1，无明确拒绝提示。源码中的离线乐观路径没有相同的余额校验，因此存在离线暂时负数的风险；本轮没有把这一风险当作已完成的离线实测。iOS 推荐保存前拒绝，保持原值，并在已有页头错误位置提示“积分不足，无法撤销”；这项可见差异列入 review。

### 视觉和反馈

- 固定浅色；紫—靛—蓝渐变页头、金币、浅色渐变背景、彩色圆角卡片。卡片 165×165、圆角 16；任务按数组索引循环 10 种渐变，奖励按 `id.length % 10` 取色，不能按奖励位置重新配色。

- Web 页头在 640 宽以下分两行；640 及以上同一行。iOS 删除锁按钮和它的 44 宽占位，窄屏操作行由“撤销模式／临时加减”两个按钮平分，其余视觉参数沿用。临时弹层窄屏靠底，宽屏居中、最大宽 448；文字、间距、图片大小以源码和截图共同对照。
- 成功普通任务／兑换／临时调整出现全屏白色 88% 遮罩和模糊，**阻挡后续点击约 2.2 秒**；16 个图标粒子下落，中心显示绿色正数或玫红负数。任务粒子优先用其 PNG；奖励粒子用配置 emoji，即使卡片使用 PNG；临时调整用 ⭐。撤销不播放庆祝或声音。
- 中心数字淡入淡出约 1.8 秒、弹跳 0.7 秒；积分变化通常在 600ms 内逐步更新，最多 30 步。Web 从显示值 0 更新时会直接采用新余额，这是源码中的例外，不应承诺每次都滚动数字。

## 3. 明确推荐的最小 iOS 方案

**已确定的存储选型：SQLite＋SwiftData。** 使用 SwiftUI、一个 `@MainActor @Observable` 状态对象和系统 SwiftData，保存本地逐笔积分记录；零第三方依赖。最低 iOS／iPadOS 17。存储选型确定不等于整体开发获批。

具体采用 SwiftData 的默认本地持久化方案：Swift 模型 → SwiftData → Core Data → SQLite 数据库文件，保存在 App 沙盒内。应用通过 SwiftData 读写，不直接操作底层 SQLite 表，也不另建一套 SQL 访问层或自定义存储。

Schema 在 Swift 代码中用 `@Model` 定义 `PointEntry`，声明字段类型、可选性及必要约束；`ModelContainer` 根据模型管理存储结构。之后若改变模型，使用框架支持的迁移机制；复杂变更再明确版本和迁移步骤，不假设所有变化都能自动兼容。第一版只需一个持久化模型，不预建迁移框架、仓储协议、服务容器、跨平台共享层或事件同步框架。

### JSON 与数据库：复核结论

`Codable` 是 Swift 数据的编码／解码机制，不是数据库，也不决定保留什么信息。需要分别决定“存储引擎”和“保存每日汇总还是每次操作”。JSON 可以存逐笔明细；数据库如果只存汇总，同样无法还原明细。

原 JSON 方案存了每日任务次数、奖励次数及临时调整净额，因此**今天、上周的任务净得分／兑换净支出／总净变化都能计算，并不困难**：取出相应日期，做乘法和求和。上周只需取七个日汇总；不能说没 SQL 就做不了统计。当前固定目录前提下，十年也只有约 3,650 个日汇总，不能仅凭数据量断言需要数据库。

真正的不足是汇总不可逆：

- 临时加 10 再减 8 与仅加 2 都只留下净额 +2；不能再分别回答“临时奖励多少、扣了多少”。
- 完成两次再撤销一次，与只完成一次都留下次数 1；不能再区分原始操作和撤销过程，不能按小时统计或追查一次误操作。
- 原方案用“次数 × 当前目录分值”重算历史；若将来发布新版本调整固定分值，旧积分会被重算。第一版虽然不支持编辑，保存动作当时的实际分数仍比依赖未来目录更稳妥。
- JSON 后来可以迁入数据库，但只能迁已有信息，不能找回已经丢弃的明细。数据库也不会自动修正上述建模问题。

| 比较项 | 每日汇总 JSON（原方案） | 逐笔 JSON | SQLite＋SwiftData 逐笔记录（已选定） |
|---|---|---|---|
| 当天／上周汇总 | 简单，取日汇总求和 | 按日期和类型筛选、求和 | 按日期和类型 fetch，再计算所需汇总 |
| 时段／操作明细、临时加减拆分 | 已丢失的信息无法恢复 | 可做，但自行遍历／组织查询 | 可筛选、排序和分批读取，不必全读历史 |
| 保存动作 | 原子重写整个汇总文件 | 单文件方案随历史增加而重写更多数据 | 由持久化引擎保存新增记录，无需应用重编码整份 JSON |
| 一致性 | 单写入者＋原子替换可满足当前需求 | 同左；不能把普通 append 当作事务 | 明确 save／失败 rollback；业务规则仍须自己校验 |
| 字段变更／维护 | 自己处理解码兼容与格式升级 | 同左 | 有 schema／迁移机制，但语义变化仍需设计与测试 |
| 代价 | 起步代码最少，信息损失最大 | 保留明细，但文件读写与查询维护增多 | 多一个 model、container/context 和持久化测试；有框架版本约束 |

如果唯一目标永远是现有界面加简单七日总分，JSON 完全够用。结合本次对历史统计的明确关切，以及 Web 本来就保留逐笔 `PointEntry`，本计划选择保留同等粒度，用 SQLite＋系统 SwiftData 管理本地数据；**原因是保留信息并减少持续维护文件存储的工作，不是宣称 JSON 无法查询，也不是为 AI／同步／多用户预建架构。**

SwiftData 不等于直接写 SQL。以 iOS 17 可用能力为基线，计划使用 `FetchDescriptor`／predicate 筛选，再以 Swift 求和；不能承诺任意 `SUM/GROUP BY/JOIN` 都能作为一个 SwiftData 查询下推。若目标是直接写复杂 SQL 报表，SQLite 更合适：它原生支持 `SUM` 等聚合及事务，但直接接系统 SQLite C API 还要处理语句、参数绑定、结果映射和 schema 升级。Core Data 也能胜任，然而本任务没有必须选它的具体需求；不同时叠加两套存储栈。

统计口径必须独立说明：例如任务得 20、兑换支出 15、临时加 3／减 2，当天任务得分为 20，净变化为 +6。撤销任务应冲减任务得分，奖励退款不能算完成任务所得。“上周”还需定义周起始日，日期边界均按 PT，使用起点包含／终点不包含的区间。数据库查询也不能替代这些业务定义。本轮不加统计入口，也不提前要求 Gordon 决定未开发报表的口径。

性能边界不夸大：假设每天 50 次操作，一年约 18,250 条、十年约 182,500 条，这是估算而非实测。当前推荐启动时分批汇总余额、日常操作只增量更新内存结果；不每次点卡片都全表重算，不预建永久汇总表。实际启动时间需要实现后测量，有证据再决定是否需要优化。

### 页面组织

启动加载本地数据后直接显示任务页；没有密码页、锁按钮、登录状态或角色概念。主页面使用一个 ScrollView，内含页头、顶部双标签和卡片；标签、撤销模式、弹层和庆祝是视图临时状态。卡片共享一个小视图，任务／奖励保留各自布局参数。弹层用 SwiftUI overlay 还原靠底／居中的 Web 位置，不引入原生 sheet 的拖拽档位或新导航。

iPhone、iPad 使用同一界面，按**可用内容宽度**重排；iPad 支持横竖屏及窗口缩小，不增加侧栏、多窗口或额外面板。安全区由系统处理，背景延伸到边缘；默认字号下对照 Web，文字用 Arial 可用字形及系统中文／emoji 回退，保留浅色外观。较大辅助字号允许文字与布局必要扩展，不以截图一致为由裁切关键操作。

### 数据和保存

- `Catalog`：静态 Task／Reward 数组，逐项保留 Web 的 ID、标题、顺序、emoji、分数和图片映射；不提供编辑入口。不把测试夹具中简化／过时的标题当正式目录。
- 唯一持久化 model 为 `PointEntry`：UUID、发生时间 `occurredAt`、PT `dateKey`、类型（task／reward／adjustment）、固定 `itemID`、实际有符号 `points`。任务完成为正、任务撤销为负；兑换为负、退款为正；临时调整按其符号记录。只接受当前目录的分值，不另存任务／奖励数据库表。
- 每次成功操作新增一条记录；撤销记录反向分值，不删除原记录，沿用 Web 的业务语义。当前撤销是“同项当天一次”，不引入指定历史操作撤销、撤销链或历史浏览功能。
- 总余额为全部记录 points 之和；当日净值为该 dateKey 的 points 之和；当日任务次数为正向条数减撤销条数，奖励次数为兑换条数减退款条数。未发生项目为 0；历史分数不从当前目录反推。
- 一个本地 `ModelContainer`、一个写入 `ModelContext`，显式关闭该 context 自动保存，使用明确的 `save()`。状态对象串行执行：取 PT 日期 → 根据已保存状态校验 → 插入记录 → save → 更新内存余额／次数 → 反馈。失败 rollback 未保存插入，展示错误，保留原显示值，不庆祝；不直接将 context 的未保存值绑定成积分 UI。
- 启动时从记录重建余额和今日计数；正常操作后只增量更新内存值，跨天重新读取当日记录。内存状态是可重建的显示结果，不增加持久化余额表、缓存同步机制或远端事件队列。
- 首次创建空库才从零开始。数据库打开／读取失败显示加载失败，**不自动删库重建或清零**。测试使用独立临时数据库；不建设备份／恢复平台。
- 显式配置本地存储（CloudKit database 为 none），不申请 iCloud 同步能力；系统设备备份不等同于产品同步。第一版安装后从零开始，不搬运 Web 生产数据。由于 iOS 尚未开发，无需编写 JSON 到数据库的迁移代码。
- 日期用 Gregorian Calendar + `America/Los_Angeles`；启动、回前台、每次动作和前台每 10 秒检查日期，后台无需运行。仅更新当天投影，不清空历史／总余额。夏令时由系统时区处理，不写死 UTC−7／−8。测试传入 `Date` 即可，不建时钟框架。

## 7. Web 对照、修复与再验证循环（开发获批后执行）

4. **记录并修复差异。** 在本文件维护简短验收表：`场景 ID｜Web 预期｜iOS 实际｜证据路径｜状态`，状态为“通过／待修复／未验证／已接受差异”。定位差异原因，优先修改对应视图参数或业务逻辑；不能通过改 Web 参照、放宽预期或删除测试掩盖不一致。
